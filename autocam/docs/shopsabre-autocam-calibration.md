# ShopSabre AutoCAM calibration — brainstorm (no code)

**Scope: "New Router" (ShopSabre Pro 408, WinCNC control) on the Fusion CAM pipeline specifically** — the Runner/Fusion path this whole app now runs plate/box-tube jobs through, not the older pure-JS `routing.js` generator. The existing UNC Router single-tool flow must keep working exactly as it does today; nothing here should change its behavior.

There's a separate, older plan (`autocam/docs/toolchange-gcode-plan.md`) for tool-changing on the legacy `routing.js` generator - different pipeline, different problem. Worth reading for the general tool-change *hazards* (re-touch-off risk, `M00` vs `M01`), but its data-model/generator-architecture sections don't apply here; the Fusion Runner pipeline already has its own tool-matching machinery (see below).

## What's already true today - checked directly, not assumed

- **The post-processor is already correctly wired.** `cam_machines.post_processor = 'shopsabre.cps'` for New Router, and `resolve_local_post_processor()` (`localCamAssets.py`) already maps that to the real, bundled `autocam/fusion/runner/postprocessors/shopsabre.cps`. That file is real - `description = "ShopSabre with WinCNC control"`, `extension = "tap"` baked in directly, and it has a genuine `hasToolChanger` property ("Specifies that a tool changer is available") plus `tool.manualToolChange` handling. Posting a job through this machine already produces `.tap`-extension output with zero extra code.
- **`controller = 'wincnc'` is correct, not a bug.** Flagged earlier this session as possibly wrong; checked the migration directly - it's deliberate (`(DEPRECATED)`'d an earlier, actually-wrong value in the same file, per its own comment). ShopSabre routers commonly ship with WinCNC control, not a Fusion-branded "shopsabre" controller type. Close that out.
- **`gcode_extension = 'tap'` exists on the machine row but isn't read anywhere in the Fusion pipeline** (`grep` across every `.py`/`.js` file in `autocam/fusion/`: zero hits). It's inert for this pipeline - the real extension already comes from the post-processor itself (`shopsabre.cps`'s own `extension = "tap"`), and `NcArtifacts.py` (`collect_nc_artifacts()`) doesn't filter by extension at all, so whatever the post actually names its output files just flows through unchanged. This column is presumably read by the *legacy* `routing.js` path per `toolchange-gcode-plan.md`; not something this plan needs to touch.
- **`cam_machines.operation_type = 'routing'` on New Router is not a blocker.** UNC Router has the identical value. This field describes the machine profile's broad category, unrelated to `cam_jobs.operation_type` (which is what actually routes a job to the Fusion Runner vs. the legacy generator - Fusion CAM jobs are always `'milling'` regardless of the machine's own `operation_type`).
- **The real blocker: `cam_machine_tools` has zero rows for New Router.** Checked directly. `can_run_plates`/`can_run_box_tubes` are both `true` on the row - so it already shows up as a selectable router in the Plates tab - but picking it hits "No tools installed on this router" immediately, since nothing is installed.
- **The multi-tool template-patching machinery already exists**, built out this session for a different reason (closing the machining-time gap): `patch_cam_template_with_tool_libraries()` already has `_required_tool_signature()` / `_find_matching_tool()` to match a template operation's own baked-in tool signature against whatever's in the selected library, and a `largest_endmill` preference now applied to `contour2d` **and** `adaptive2d`/`pocket2d` roughing operations (this session's `yuvan/multi-tool-roughing-readiness`). None of this is New-Router-specific; it's generic and already exercised daily on UNC Router with a one-tool library (a confirmed no-op there). It should work unmodified the moment New Router's library has more than one tool in it.
- **Confirmed directly (not inferred from tool descriptions): UNC Router does not do tool swaps; New Router does.** This is the actual, physical, machine-level dividing line for what each router can run - not a Fusion/software limitation to work around, a real hardware fact to design around.
- **Follows directly from that: countersinking is New-Router-only.** A countersink needs its own dedicated bit, physically different from the main endmill - cutting one mid-job means a tool change. Since UNC Router can't swap tools at all, it can never run a countersink operation, full stop; New Router is the only machine in the shop this pipeline could ever offer that operation type on. More generally: **any operation whose real tool differs from the job's main endmill (countersink today, plausibly others later) is inherently New-Router-only** - the Fusion CAM job-queueing UI/logic should reflect that constraint (not offer/accept such an operation for a single-tool machine) once this is built, rather than let a UNC Router job silently request something it physically cannot do.

## What was found live in Fusion's own tool libraries (via the MCP bridge)

Five real cloud tool libraries exist in this Fusion account, queried directly (not guessed):

| Library | Tool count | Notable contents |
|---|---|---|
| `Normal router tools (use this)` | 7 | 4mm flat end mill *("sized for toolchanger")*, 0.25in (6.35mm) flat end mill *("for tool changer")*, **6mm flat end mill *("6mm for toolchanger")***, 0.201in drill *("for toolchager")*, two 82° countersinks, "971 Main Bit" (4mm) |
| `971 Tools` | 15 | Same 4mm/6mm/0.25in toolchanger-labeled set, plus a `#43` and `0.201in` short drill, chamfer mill, ball end mill, 2in face mill, a second "971 6mm 1 flute Bit" |
| `2026 gear` | 5 | Several "971 Main Bit" diameter variants (1/8in, 5/32in, 4mm), a 6mm toolchanger bit |
| `Manual Tools` | 21 | General shop tool inventory - drills (#-size and fractional), taps, a reamer, a 2in face mill. Not toolchanger-specific. |
| `foam testing` | 1 | A single "FOAM ONLY" endmill - not relevant here. |

Several tools across these libraries are explicitly labeled **"for toolchanger"** in their own description - real, direct evidence this router has an actual automatic tool changer, not just a manual-swap setup. And critically: **a real 6mm endmill already exists** in the shop's own tool library, the same diameter the manual reference program (`practice.ngc`) uses specifically for its bulk-clearing "BIG ENDMILL" operation - the exact tool this session's machining-time investigation (issue #375) identified as the likely gap between our ~19min and the reference's ~10min on the same part.

`Normal router tools (use this)` reads like the one meant to be the canonical source - its own name says so - and lines up closely with New Router's existing `default_params.toolDiameter: 0.25`, itself already anticipating the 0.25in toolchanger bit.

## Open questions - genuinely unknown, need a real answer before building

1. **Confirmed: New Router does tool changes, UNC Router does not.** Still open: is it a true *automatic* changer (fast, no operator pause needed) or a manual carousel (operator swaps physically, matching the tool descriptions' own "toolchanger" wording, which doesn't by itself distinguish the two)? The post-processor supports both (`hasToolChanger` property, `tool.manualToolChange` handling) but doesn't default one way on its own within this pipeline - `_apply_tool_to_elem`/`patch_cam_template_with_tool_libraries` never sets this property today (it's never been exercised with more than one tool). If automatic, tool changes are fast and need no operator pause. If manual, the post's `manualToolChange` path needs the same re-touch-off caution `toolchange-gcode-plan.md` already worked out for the legacy generator - a real physical fact to confirm with whoever runs this machine, not something to guess from tool names alone.
2. **Which library is actually "the" one?** Multiple libraries have overlapping tools (4mm/6mm show up in at least three). `patch_cam_template_with_tool_libraries` already accepts a list of library paths and searches across all of them (`tool_library_paths: list[str]`) - so this may not need a hard choice, but duplicate near-identical tools across libraries could make `_find_matching_tool`'s selection nondeterministic (which 4mm bit does it pick when three qualify?) unless there's already a real tiebreak rule. Worth checking `_select_tools`/`_find_largest_endmill`'s actual tie-handling before relying on it with a multi-library, multi-duplicate set.
3. **Does the real exported ShopSabre-appropriate CAM template even exist yet?** `_select_plate_template_path` already has a mapping for `machine == "new router"` + metal/Lexan material to `new router metal sheet (shopsabre only!!).f3dhsm-template` - confirm this file is a *real* Fusion export from this specific machine (tool numbers, WCS setup, retract heights all correct for it), not a placeholder/copy of the UNC Router one. If it's a copy, its `<tool>` signatures likely still describe the UNC Router's single 4mm bit, same trap the earlier "template's own baked-in tool signature" investigation found for adaptive2d/pocket2d operations this session.
4. **Real tool numbers / turret slots.** A real ATC needs each tool to reference a consistent physical slot number (matches `toolchange-gcode-plan.md`'s own `tool_number` proposal for the legacy generator) so the post-processor's tool-change block calls out the correct one - does WinCNC's tool table already assign these, or does Fusion's own tool library `number` property need to be set per tool and kept in sync with the physical carousel?
5. **`toolChangeTime` calibration for machining-time reporting.** This session's `getMachiningTime()` call uses `toolChangeTime=15` (seconds), calibrated against the *manual* M6-pause pattern in `practice.ngc` (confirmed: its own "3 tool changes @ 0:45 total" = 15s each). A real ATC's actual tool-change time is very likely different (often faster) - needs a real, physically-timed swap on this machine before the number in code is trusted for this machine specifically, not just carried over from the manual-swap assumption.
6. **Roughing-vs-finishing tool split - direct instruction: New Router should use different bits per operation for real efficiency, not just correctness.** This session's `largest_endmill` preference change always picks the single *biggest* tool for adaptive2d/pocket2d roughing. With a real multi-tool library that's directionally right for roughing (clears bulk material faster with a bigger diameter - the whole point of issue #375's finding), but finishing/small-feature operations (`Feature Slot Cut`, the two per-hole finishing passes) may want the *smallest* appropriate tool for tight internal corners instead, and the dedicated small drill/countersink tools obviously need their own specific ones, not the roughing endmill. That distinction doesn't exist in the patching logic today - needs a real per-operation-category tool preference (roughing -> biggest fitting endmill, finishing -> smallest fitting endmill, drill/countersink -> the one tool of that exact type), not just the single blanket "biggest tool wins" rule currently applied to everything contour2d/adaptive2d/pocket2d.

## Rough phased plan (once the above questions have real answers)

1. **Confirm, don't build**: verify with whoever runs the ShopSabre whether it's a true ATC or manual-carousel, and get real physical tool numbers for whatever set gets installed in `cam_tools`.
2. **Populate `cam_tools`/`cam_machine_tools` for New Router** from the confirmed library (`Normal router tools (use this)` is the leading candidate), matching the real diameters/types found above - same shape as UNC Router's existing single-tool row, just more of them.
3. **Single-tool parity check first** - direct instruction from earlier this session ("it should also work how it is right now"): queue one real single-tool plate job on New Router before touching anything multi-tool, confirming template selection, post-processing, and `.tap` output all work exactly like UNC Router does today, just with a different post and extension. This is the actual regression-safety gate.
4. **Confirm the template's per-operation tool signatures are real** (open question 3) - if `new router metal sheet (shopsabre only!!).f3dhsm-template` needs re-exporting from a real ShopSabre-configured setup, that has to happen before multi-tool matching means anything.
5. **Exercise real multi-tool matching** on a simple job once (2) and (4) are confirmed - verify `_find_matching_tool`/`largest_endmill` picks sensible tools per operation with the real multi-tool library in place, and resolve the tie-break question (2) if it turns out to matter in practice.
6. **Wire up `hasToolChanger`** (or the manual-swap path, per whichever answer (1) turns out to be) in `_apply_tool_to_elem`/the template patcher.
7. **Build the per-operation-category tool preference** (open question 6) - roughing gets the biggest fitting endmill, finishing the smallest fitting one, drill/countersink operations their own dedicated tool type - instead of today's single blanket "biggest tool wins" rule.
8. **Gate New-Router-only operation types** (countersink today) out of the UI/queueing path for single-tool machines, so a UNC Router job can't be asked to do something it physically cannot.
9. **Real physical test cut** - verify actual tool-change behavior and timing on the machine itself, then recalibrate `toolChangeTime` for this machine specifically (open question 5) rather than reusing the manual-swap-derived 15s.

## Non-goals for this plan

- Does not touch the legacy `routing.js` / `toolchange-gcode-plan.md` path at all.
- Does not change UNC Router's behavior in any way - it stays single-tool exactly as today.
- Does not attempt to guess/default `hasToolChanger` without a real answer from whoever runs the machine.
